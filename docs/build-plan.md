**Status:** done

**Contents:**
- GitHub repo `AI-Wise-IT/hatch-cli` created (public — see ADR-0004 correction below).
- CLI scaffold: `package.json` (`@ai-wise/hatchcli`), TypeScript strict config, Biome (lint/format), Vitest with a first unit test, a minimal CLI entrypoint that builds, runs, and prints its own version.

- `@ai-wise/hatchcli` published publicly on npm: `0.0.0` as a one-time manual bootstrap publish (required to claim the name before a Trusted Publisher could be configured), `0.0.1` as the first fully CI-driven, OIDC-authenticated release.

**Rationale:** Always the first batch, unconditionally — nothing else can be reviewed as a coherent, demoable whole once quality gates are meant to be active until the gates themselves exist. This is the walking skeleton (Cockburn): a thin, real connection through every layer — repo, CI, branch protection, release pipeline — proven end to end before any product/use-case code exists. See `plan-build-batches/references/batching-criteria.md` for the full reasoning.

- Branch protection: attempted a direct push to `main` and confirmed it was rejected (`GH006: Protected branch update failed`); then opened a PR with the same change, watched the required `checks` status check pass, and confirmed it merged with zero approving reviews.
- Release pipeline: pushed the `v0.0.1` git tag, watched `release.yml` run, and confirmed `@ai-wise/hatchcli@0.0.1` appeared on the public npm registry with an `attestations.provenance` field (proof of OIDC trusted-publish origin, not a manual upload).
- Ran `npx @ai-wise/hatchcli@latest` for real and confirmed it printed the correct, dynamically-read version and exited `0`.

**Notes — architecture corrections discovered during this batch:**
- ADR-0006: package name corrected twice — `hatch-cli` was unavailable, then unscoped `hatchcli` was rejected by npm's anti-typosquatting check; settled on the scoped `@ai-wise/hatchcli`.

- ADR-0007: publish authentication corrected from a stored `NPM_TOKEN` secret to npm Trusted Publishing (OIDC) — `npm token create` is blocked for accounts on granular access tokens, and a stored long-lived token is exactly what Trusted Publishing exists to eliminate.

Out of scope for this batch: the skill-content repo (a separate GitHub repo, not yet created) needs its own infrastructure batch when that work starts — including its own resolution of the same private-repo-vs-branch-protection constraint hit here.

UC-5's own destination-path-collision detection logic is deliberately *not* built here; it remains its own later use-case batch, added as a second required status check alongside `version-check` when that batch is built.

## Batch 3 — Authenticate to the Registry

**Status:** done

**Contents:** `hatch login` (UC-2): main flow (prompt for the registry's GitHub PAT, validate, persist per [0005-auth-token-env-file-precedence](architecture/decisions/0005-auth-token-env-file-precedence.md)) and AF-1 (invalid password). Token validation calls GitHub's `GET /user` — the lightest authenticated call available, proving the token is a live GitHub credential without requiring any scope or reaching the private skill-content repo itself (that repo-specific reachability check belongs to later batches' fetch logic, not login). The env-var-first, file-fallback credential resolution (`resolveToken()`) is exposed as a standalone, importable module (`src/auth/credentials.ts`) rather than buried in the login command, so later batches (bootstrap, import) can reuse it directly.

**Rationale:** Nothing else in the CLI can be demoed without it — the PRD's own sequencing notes state login must ship before or alongside private-skill support. No dependency on any other remaining batch.

**Verification:** All of the following were directly observed, not inferred from code:
- AF-1 (invalid token): ran the built CLI with a garbage token — rejected with `hatch login: invalid password (GitHub rejected the token as invalid or expired) — nothing was changed.`, exit code `1`, and confirmed `~/.hatch/credentials.json` was not created.
- Main flow (valid token): the developer ran `hatch login` with a real, short-lived GitHub personal access token (revoked immediately after testing) — confirmed the success message printed, exit code `0`, and `~/.hatch/credentials.json` created with the expected `{ token }` shape.
- `HATCH_TOKEN` precedence: with the file already populated from the step above, the developer set `HATCH_TOKEN` to a different value and confirmed `resolveToken()` returned the env var's value rather than the file's. This didn't need a second real GitHub token, since `resolveToken()` resolves the precedence without re-validating against GitHub — that validation only happens inside `hatch login` itself.
- Backing automated coverage: unit tests for credential precedence, file persistence with restrictive permissions (skipped on Windows, where POSIX file-mode bits don't apply), and GitHub token validation via `msw`-mocked responses (200 / 401 / network-failure).

**Notes — implementation detail discovered during this batch:**
- Hit and fixed a native crash on Windows while wiring this up: calling `process.exit()` directly while an in-flight `fetch`/undici handle was still finalizing tripped a libuv assertion (`UV_HANDLE_CLOSING`, `src/win/async.c`). Fixed by using `process.exitCode` assignments instead of `process.exit()`, letting Node exit naturally once pending work settles — applies to the CLI entrypoint and the login prompt's Ctrl-C handling.

## Batch 7 — Import: re-import & staleness

**Status:** done

**Contents:** UC-3 AF-1 (already up to date), AF-2 (update available), AF-3 (local edits present), AF-4 (deprecated/removed detection, clarified as a metadata flag per ADR-0013 — never a deletion). Also AF-10, AF-11, AF-12 (standalone version pinning: `hatch import <name>@<version>` exact/sticky pin, `hatch import <name>@^<version>` range/floor pin, `hatch import <name>@latest` to clear a pin, and re-import respecting a standing exact pin instead of auto-updating) — folded into this batch's scope via [rescope-0001-standalone-version-pinning](../intake/rescope-0001-standalone-version-pinning.md), since pin-vs-auto-update is the same re-import-semantics machinery this batch already builds. `hatch.manifest.json` moves to schema v3, adding a per-skill `contentHash` and `pin` field (one migration, two additive fields). Adds three small pure-function modules — `src/registry/semver.ts` ("newer compatible version" per ADR-0009), `src/manifest-migrations/content-hash.ts` (SHA-256 over a skill's placed content), `src/manifest-migrations/pin-spec.ts` (`<name>@<spec>` parsing) — that `src/commands/import.ts`'s re-import decision logic is built on: every fetch is now gated by a version/pin check before touching the registry or filesystem, and local-edit protection is applied uniformly, including across an explicit re-pin, since UC-3's "never overwrite a local edit" business rule is stated unconditionally rather than scoped only to a bare re-import.

Three format gaps were surfaced to the developer and settled before writing code against them, mirroring the 0015/0016/0017 precedent from Batches 5–6:
- [0018-manifest-content-hash-local-edit-detection](architecture/decisions/0018-manifest-content-hash-local-edit-detection.md): a per-skill `contentHash`, computed from the primary declared harness's placed content (excluding `skill.json` and any AF-6 skip/suffix outcome), recomputed purely locally at re-import time — no extra registry fetch.
- [0019-registry-removed-metadata-flag](architecture/decisions/0019-registry-removed-metadata-flag.md): a plain boolean `removed` field on a skill/group's own `skill.json` — no separate "deprecated" state, since nothing in this system ever branches on that distinction.
- [0020-standalone-version-pin-manifest-and-parsing](architecture/decisions/0020-standalone-version-pin-manifest-and-parsing.md): a `pin: {type, value}` manifest field (the same v2→v3 migration as 0018) and the `<name>@<spec>` argument-parsing rules (split on the last `@`; `latest` / `^<semver>` / bare literal).

**Notes — implementation decisions made within this batch's scope (not full ADRs, per ADR-0018's own explicit deferral):**
- A pre-Batch-7 (v1/v2) manifest entry has no baseline `contentHash` to compare against on its first post-upgrade re-import. - Local-edit protection (the hash-mismatch check) is applied uniformly across every re-import path — a bare re-import, an explicit re-pin, and a pin-clearing `@latest` — rather than being scoped only to AF-2's literal wording, since UC-3's Business Rules state "placed content is never overwritten if it differs from what was originally imported" unconditionally.
- An exact/range pin is resolved against the plain (unsuffixed) top-level registry name's own version-tag sequence; a harness-suffixed variant's independent version history (if one ever exists for a pinned skill) isn't addressed by this MVP — not exercised by any current registry fixture.

**Addendum — two gaps found during developer review, resolved and built as a follow-up within this batch:**
- A registry folder's `skill.json` was the only filename ever excluded from deployment — `NOTE.md` (fixture-authoring documentation, e.g. `_harness-suffix-fixture`, `_reimport-fixture`) was being copied straight into target projects, unnoticed since no real (non-fixture) skill had ever carried one. ## Batch 8 — Remove Content from a Project

**Status:** done

**Contents:** `hatch remove <name>` (UC-4 main flow) plus AF-1 (not imported), AF-2 (manifest/disk drift), AF-3 (local edits present), AF-4 (skill-in-group refusal). Per [0022-remove-force-flags-not-prompt](architecture/decisions/0022-remove-force-flags-not-prompt.md), AF-2/AF-3 are gated by `--force-all`/`--force-clean` flags rather than an interactive prompt, for both a standalone and a group target: by default, any dirty item (missing or locally-edited content, detected via the same `contentHash`/`hashFromDisk`-family mechanism Batch 7 established) aborts the whole operation and names every affected item; `--force-all` removes everything regardless; `--force-clean` removes only what's clean, leaving dirty items in place. Adds `hashDiskTree`/`diskTreeIsEmpty` (`src/manifest-migrations/content-hash.ts`) — `hatch remove` has no registry fetch to supply an expected file list the way `hatch import`'s re-import path does, so drift/local-edit detection instead walks whatever currently exists on disk under a skill's primary-harness directory. A group's own top-level manifest entry is dropped only once every one of its members has actually been removed, so a `--force-clean` partial removal never leaves a surviving member's `group` field pointing at an entry no longer in the manifest.

**Rationale:** Depends on Batch 5 and Batch 6 — needs previously-imported standalone skills and group members to remove; AF-4's group-membership refusal specifically needs Batch 6's group tracking.

**Verification:** All of the following were directly observed against the real registry, not inferred from code or tests alone, in a scratch project (`node dist/index.js remove ...`):
- Main flow: imported `hatch-usage`, then removed it — content and manifest entry gone under `.claude/skills/`, exactly one new commit (`hatch remove: remove "hatch-usage"`), working tree clean.
- AF-1: re-ran remove for the same (now-removed) name — `"hatch-usage" was never imported — nothing to remove.`, exit `0`, no new commit; also confirmed for a name never imported at all and for a project with no manifest yet.
- AF-2: imported `prd-elicitation`, manually deleted its placed folder outside Hatch, re-ran remove with no flag — `"prd-elicitation" was not removed — ... its placed content is missing from disk.`, exit `0`, manifest entry left in place, no new commit; re-ran with `--force-all` — stale entry dropped, one commit.
- AF-3: imported `hatch-usage` again, hand-edited its placed `SKILL.md`, re-ran remove with no flag — `... has local edits since it was imported.`, exit `0`, content and manifest entry untouched, no new commit; re-ran with `--force-all` — removed despite the edit, one commit.

**Notes — implementation decisions made within this batch's scope:**
- AF-2's "content missing on disk" is detected as the primary declared harness's skill directory not existing (or existing but recursively empty) — distinct from AF-3's hash-mismatch-on-existing-content signal — consistent with `contentHash` itself only ever being computed from the primary harness's placed content (0018).
