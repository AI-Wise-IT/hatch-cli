# Registry discovery: a live walk over the contents API, with descriptions read from wherever each kind of content already keeps its prose

## Metadata

- **id:** 0028-registry-discovery-live-walk
- **component:** registry-discovery
- **status:** accepted
- **applies_to:** `hatch list` and everything behind it (`src/commands/list.ts`, `src/registry/fetch.ts`'s root listing, `src/registry/description.ts`, `src/registry/group-resolve.ts`'s `description` parsing); the `description` field on every top-level folder's `skill.json` in the skill-content repo (hatch-skills) and that repo's content checks; the `description` key in every plain skill folder's `SKILL.md` frontmatter
- **decision_record:** `docs/architecture/decisions/0028-registry-discovery-live-walk.md`

## Decision

`hatch list` discovers the registry's importable content by **walking it live on every invocation**, over the same GitHub contents API [0003-registry-github-tarball-fetch](0003-registry-github-tarball-fetch.md) settled on. There is no index file. One non-recursive call on the repository root yields every top-level entry's name and type; each surviving candidate costs one `skill.json` fetch, plus one `SKILL.md` fetch when that folder turns out to be a plain skill. The per-entry fetches are independent and run through a bounded concurrency pool.

A CI-maintained `index.json` at the registry root is named here as the **escape hatch** if registry growth ever makes the walk slow, and is deliberately not built. It is a drop-in substitute: it would replace the retrieval step behind the same command, the same output and the same requirements, so adopting it later changes no observable behavior beyond speed.

**Every name filter and every name-decidable exclusion runs before any per-entry fetch.** The root listing already carries the names, so the caller's filter and the `_`-prefix testing exclusion both cost nothing — the same ordering [0027-testing-skill-convention](0027-testing-skill-convention.md) chose for `hatch import`. Exclusions that need metadata — `removed: true`, and the `"testing": true` declaration backstop for a folder that reached the registry without the prefix — necessarily apply after that folder's `skill.json` is read, dropping the entry from the rendered output rather than from the fetch set.

**A description is read from wherever that kind of content already keeps its own prose.** A plain skill's description is read from the `description` field in its `SKILL.md` frontmatter, and never from its `skill.json` — that frontmatter is what governs how the skill actually behaves once placed, so a second authored copy could misdescribe it in exactly the listing meant to help. A group has no `SKILL.md` of its own, so a group's description is read from a new **`description` field on the group's own `skill.json`**, joining `version`, `members`, `removed` and `testing` as one more additive optional field on the same manifest — the shape [0016-group-member-manifest-format](0016-group-member-manifest-format.md) and [0019-registry-removed-metadata-flag](0019-registry-removed-metadata-flag.md) each chose over a separate file. A group's description is never derived by joining its members' descriptions, and a group's `SKILL.md` is never fetched.

The registry's content checks require a non-empty string `description` on every group folder's `skill.json` and a `description` in every plain skill folder's `SKILL.md` frontmatter. The CLI, however, tolerates its absence at every stage: a description that cannot be read — no `SKILL.md`, no frontmatter, no key, a value that is not a non-empty string, or a version published before the field was required — still lists the entry, with its description shown as absent. An unreadable `skill.json` is different in kind: kind, version and removed-status are all unknown, so the entry cannot be rendered honestly at all, and it is reported by name with a non-zero exit while every readable entry still prints.

Frontmatter is parsed **narrowly, without a YAML dependency**: the leading `---` fenced block is read for a single `description` key — a plain scalar on one line, a quoted value, or a folded value spanning lines until the next key. Anything the reader cannot make sense of yields no description rather than an error.

**A `<base>-<code>` folder is folded into `<base>` only when a top-level `<base>` folder also exists.** That is exactly the case `resolveSkillFolderName` resolves to the variant, and the only case decidable from a single snapshot. Every other top-level folder is listed under its own literal name — including one shaped `<base>-<code>` with no plain sibling, which is indistinguishable from an ordinary skill whose name merely ends in a reserved code ([0025-harness-shadowing-risk-accepted](0025-harness-shadowing-risk-accepted.md)) and whose literal name `hatch import` does accept. The reserved codes are read from `src/harness-registry.json` ([0001-harness-suffix-convention](0001-harness-suffix-convention.md)), never hardcoded.

**A `404` on the registry root reports a credential problem, and only there.** The root exists for anyone who can see the repository, so a `404` on it has exactly one reading: the credential in use cannot see the registry. `hatch list` says so, and never describes that result as a name that was not found. `hatch import`'s per-name `404` stays genuinely ambiguous and its not-found wording is unchanged — [0027](0027-testing-skill-convention.md) depends on that wording being identical across a genuine miss and a refusal.

## Context

A cloud-agent test of the `hatch-usage` skill ran `hatch import prd-elicitor`, guessed the name from context, and failed — the real name is `prd-elicitation`. Nothing in the CLI could answer "what is this actually called?": no `hatch list`, no `hatch search`, no browsable index. The agent's only recourse was a raw GitHub contents call against the private `hatch-skills` repo, which is neither a supported code path nor something every credential holder can do, and `hatch-usage/SKILL.md` worked around the gap by instructing agents to stop and ask the user for the exact name. [UC-3](../../use-cases/import-content.md) opens with `hatch import <skill-or-group-name>` and never says where that name comes from; discovery was the one step of the workflow with no command behind it.

What constrained the mechanism:

- **`src/registry/fetch.ts` had three call shapes, none of which listed the root.** `registryFolderExists` is a single non-recursive call used as a boolean, `fetchRegistryFile` pulls one file, `fetchRegistryFolder` walks a subtree. A directory call already returns an array of `{name, path, type}`; the root listing is that same call with the path `""`, exposed as a real result instead of discarded.
- **The contents API returns directory entries without file contents.** A directory response carries names and types; a file's base64 content comes only from a call naming that file. Per-entry metadata therefore costs one call each, and the API [0003](0003-registry-github-tarball-fetch.md) settled on has no batched form of it.
- **A folder's `skill.json` already answers three of the four things a listing needs.** `version`, `members` (present means group) and `removed` are parsed today by `parseGroupSkillJson`, on a fetch `hatch import` already makes to classify a target. Only the description was new — and only for plain skills, whose prose lives in a different file.
- **[0009-skill-versioning-semver-tags](0009-skill-versioning-semver-tags.md) rejected a version-to-commit index and [0019](0019-registry-removed-metadata-flag.md) rejected a removed-names index**, both for the same reason: a second artifact that must always agree with the tree it describes.
- **[0025-harness-shadowing-risk-accepted](0025-harness-shadowing-risk-accepted.md) established that a lone `<x>-<code>` folder is structurally indistinguishable from an ordinary skill ending in a reserved code.** Any single-snapshot folding rule has to be sound under that.
- **[0027-testing-skill-convention](0027-testing-skill-convention.md) closed by naming this surface** — "a future registry discovery surface has to decide whether testing skills appear in listings; this record settles only that they cannot be imported." This record answers it: they are omitted from an ordinary project's listing, and appear only in a project recording `testProject: true`.
- **The registry holds fifteen top-level folders today** — twelve `_`-prefixed fixtures and three real entries. A per-entry walk costs roughly thirty calls at that size, against an authenticated rate limit of 5,000/hour.
- **Scriptable output is a permanent No**, and local caching of fetched registry content is another — both on the PRD's own No list (`intake/product-requirements.md`). Neither is reopened here.

The decision itself was settled with the developer in the `add-registry-listing` change's proposal and design (`openspec/changes/add-registry-listing/`), which this record makes citable from outside that change.

## Alternatives Considered

- **A CI-generated `index.json` at the registry root, fetched in one call.** The faster mechanism, and the wrong one to build now: it is a second artifact that must always agree with the tree it describes, which is precisely why [0009](0009-skill-versioning-semver-tags.md) and [0019](0019-registry-removed-metadata-flag.md) each rejected an index. Building it also means a CI job and a generator in `hatch-skills` before `hatch list` could do anything at all in `hatch-cli`, for a latency problem this registry's size does not have. Recorded above as the escape hatch instead.
- **The Git Trees API with `recursive=1`.** Returns the whole tree in one call — but still only paths, no contents, so it saves the root call and nothing else while adding a second API surface alongside [0003](0003-registry-github-tarball-fetch.md)'s.
- **GraphQL, batching the blob fetches into one request.** A real saving, and a different API from the one [0003](0003-registry-github-tarball-fetch.md) settled on — a materially larger change than the problem justifies. Stays available if the index is ever revisited.
- **Requiring `description` on every folder's `skill.json`, skills included.** One uniform read and one fetch fewer per skill. Not chosen: it creates two authored copies of one sentence with no check that they agree, and the frontmatter copy is the one that governs the skill's actual behavior. The extra call buys the guarantee that the printed description is the one the skill carries.
- **Deriving a group's description by joining its members'.** Rejected outright: it produces a paragraph per row, and it describes the parts rather than the whole — the opposite of what a browsing reader needs.
- **A real YAML parser for the frontmatter.** More correct in general, and not worth a dependency for one known key in a block authored to a fixed convention. The narrow reader's failure mode is a missing description, which this record already treats as an ordinary listable state.
- **Listing every top-level folder literally, variants included, folding nothing.** Simpler, and rejected because it prints `handover-cld` next to `handover` as if they were two importable things — a wrong-name failure of exactly the kind this command exists to remove.
- **Inferring a family from a lone suffixed folder** (printing `handover` for a registry holding only `handover-cur`). Rejected: it prints a name that resolves to nothing, which is worse than printing a suffixed name that does resolve.
- **Aborting the whole listing when one entry's `skill.json` will not parse.** Not chosen, in favour of the shape `check-collisions` already uses — print everything readable, name what was not, exit non-zero — so one bad folder cannot deny the developer the other fourteen.
- **Filtering after the fetches rather than before.** Would make `hatch list prd` cost the same thirty calls as a bare run, for no behavioral gain.

## Trade-offs Accepted

- **Prompt coherence:** high. Three rules state the whole mechanism — "walk it live, no index"; "a description is read from wherever that kind of content already keeps its prose"; "fold `<base>-<code>` only when `<base>` exists". The asymmetry between a skill's frontmatter and a group's `skill.json` is the one thing an agent could get wrong, and it is stateable in a sentence rather than being a list of exceptions.
- **Failure surface:** the walk's cost grows linearly with the registry — roughly two calls per top-level folder, run concurrently, with filtered runs paying only for matches. A run that does hit a rate limit surfaces as the per-entry read failure path (readable entries printed, unreadable ones named, non-zero exit) rather than as a silently short list, so an incomplete listing is never mistaken for a complete one. A harness-exclusive family with no plain folder lists under its suffixed name; that is [0025](0025-harness-shadowing-risk-accepted.md)'s accepted ambiguity appearing on a new surface, not a new problem. The narrow frontmatter reader can mis-parse an unusual `SKILL.md`, degrading to a missing description — a listable state that nothing about the entry's name, kind or version depends on. And a group's `description` is authored prose about a folder whose members change: no check can verify it stays accurate, so the check requires only that it be present and non-empty and accuracy stays an ordinary content-review matter, exactly as it already is for a skill's frontmatter.
- **Reversibility:** high for the mechanism and low for the field. The retrieval step is designed to be swapped for the index behind an unchanged command, unchanged output and unchanged requirements — nothing in the requirements names the mechanism. The `description` field on a group's `skill.json`, by contrast, is published content: once groups carry it, its shape is fixed by everything already published under it, the same reasoning [0019](0019-registry-removed-metadata-flag.md) recorded for `removed`.
- **Operational simplicity:** the CLI adds one call shape to a module that already had three, and no new dependency. `hatch list` is a new command that nothing depends on, creates no manifest, places no content and makes no commit, so there is no rollback beyond not shipping it. The cost is two new content checks in `hatch-skills` and a `description` on every folder already published there, each with the version bump [0009](0009-skill-versioning-semver-tags.md)'s blocking check requires.

## Consequences

- `src/registry/fetch.ts` gains a root-listing call whose result shape distinguishes three outcomes — success, unreachable, and a root `404` as its own reason, separate from the shared `not-found` used for a named folder. Nothing else may collapse those two.
- `GroupSkillJson` gains an optional `description`. Absent, empty, whitespace-only or non-string reads as no description and never as an error, so versions published before the field stay parseable and listable forever through pins.
- `hatch-skills` must add a non-empty `description` to every group's `skill.json` and a `description` to any plain skill's `SKILL.md` frontmatter lacking one, each with a PATCH bump, **before** the content check requiring them becomes blocking — the same two-step order [0027](0027-testing-skill-convention.md) used for its mandatory `testing` field. The resulting `<name>@<version>` tags are additive; the tags the pin fixtures depend on are untouched.
- The new content check is evaluated across the whole registry rather than only the diff, and is wired into `hatch-skills`' CI as a blocking job alongside `version-check`, `name-permanence-check` and the testing-convention checks. It locks no name in, so it is blocking from the day it lands rather than waiting for the hardening cutover.
- The registry `README.md` must document the group `description` field and the skill frontmatter requirement — every rule the check enforces, none enforced but undocumented.
- `hatch-usage/SKILL.md` stops telling agents that no discovery mechanism exists and points them at `hatch list` — updated only once a released CLI actually carries the command, and naming the version it first shipped in.
- [UC-3](../../use-cases/import-content.md)'s preconditions currently assume the caller already knows the target's name; [UC-6](../../use-cases/discover-registry-content.md) is where that name now comes from.
- Any future per-version view — listing a name's published tags, or showing an older version's description — is out of scope here and reads this record first: `hatch list` shows the current version on the default branch and nothing else.

## Agent Rules

- MUST discover registry content by a live walk over the contents API — one non-recursive root call, then one `skill.json` per surviving candidate and one `SKILL.md` per surviving plain skill — MUST NOT introduce an index file, a second retrieval mechanism, or a between-run cache of fetched registry content.
- MUST apply the caller's name filter and the `_`-prefix testing exclusion to candidate names before any per-entry fetch.
- MUST read a plain skill's description from its `SKILL.md` frontmatter — MUST NOT read a plain skill's description from its `skill.json`.
- MUST read a group's description from the `description` field on the group's own `skill.json` — MUST NOT fetch a group's `SKILL.md`, and MUST NOT derive a group's description from its members' descriptions.
- MUST give every group folder's `skill.json` a non-empty string `description`, and every plain skill folder's `SKILL.md` frontmatter a non-empty `description`.
- MUST list an entry whose description cannot be read, showing the description as absent — MUST NOT treat a missing description as an error and MUST NOT omit the entry for it.
- MUST parse `SKILL.md` frontmatter narrowly for the single `description` key, without a YAML dependency, yielding no description for anything it cannot make sense of — MUST NOT raise from the frontmatter reader.
- MUST fold `<base>-<code>` into `<base>` only when a top-level `<base>` folder also exists, taking the folded entry's kind, version and description from the plain folder — MUST NOT infer a family from a lone suffixed folder, and MUST list every other top-level folder under its own literal name.
- MUST read the reserved harness codes from `src/harness-registry.json` — MUST NOT hardcode them.
- MUST report a `404` on the registry root as credentials that do not grant access to the registry — MUST NOT describe that result as a name that was not found, and MUST NOT change `hatch import`'s per-name not-found wording.
- MUST print every readable entry and name the unreadable ones with a non-zero exit when an individual entry's metadata cannot be read — MUST NOT abort the whole listing over one unreadable folder, and MUST NOT exit zero on a partial listing.
- MUST print no entries and exit non-zero when the registry is unreachable or its root cannot be read.
- MUST omit an entry declaring `removed: true` from the listing regardless of the project or the filter, and MUST NOT provide a flag that overrides it.
- MUST omit testing content from the listing of any project that does not record `testProject: true`, determining the opt-in from the manifest of the directory the command runs in and treating a directory with no manifest as an ordinary project — MUST NOT indicate that anything was withheld, report a count of hidden entries, or name the opt-in.
- MUST report a filter that matches nothing with the same wording whether it matched nothing at all or matched only hidden testing content, exiting zero in both cases.
- MUST list only top-level folders, sorted ascending by name independently of the registry's return order — MUST NOT list a group's nested member as an entry of its own.
- MUST show only the current version on the default branch and its description — MUST NOT enumerate an entry's published version tags or show an earlier version's description.
- MUST leave every project untouched: `hatch list` places no content, writes no manifest and makes no commit, and MUST run to completion from any directory whether or not a manifest is present — MUST NOT report a missing manifest or name `hatch init`.
- MUST print human-readable text — MUST NOT add JSON or otherwise scriptable output.

## Invariants

- **MUST give every group folder's `skill.json` a non-empty string `description`.** Becomes irreversible once: real groups are published carrying the field — its shape is then fixed by everything already published under it, and switching to a richer description format later would have to handle every group already published under this one. This is the same reasoning [0019](0019-registry-removed-metadata-flag.md) recorded for `removed` and [0027](0027-testing-skill-convention.md) for `testing`. Enforcement mechanism: `hatch-skills`' content check, evaluated across the whole registry. Current mode: not-yet-built — blocking from the day it lands, since it locks no name in; it may only land after every existing group already carries the field.
- **MUST give every plain skill folder's `SKILL.md` frontmatter a non-empty `description`.** Becomes irreversible once: the harnesses and `hatch list` both read that one key — it is already the field the harnesses require, so this record makes an existing dependency mandatory rather than creating a new one. Enforcement mechanism: the same `hatch-skills` content check. Current mode: not-yet-built — blocking from the day it lands, after task 4.2's content backfill.
- **MUST NOT change `hatch import`'s per-name not-found wording.** Becomes irreversible once: it already is — [0027](0027-testing-skill-convention.md) depends on that wording being byte-identical across a genuine miss and a testing-content refusal, so any divergence makes testing content distinguishable to a project that has not opted in. Enforcement mechanism: `hatch import`'s existing unit tests over the missing-name, missing-pinned-ref and testing-refusal paths. Current mode: advisory — the tests detect a regression, but nothing structurally prevents a new caller from composing a different message.

Nothing else in this record is irreversibility-bearing. The retrieval mechanism, the fold rule, the root-`404` reading, the exclusions, the ordering and the output format are all runtime behavior of a command nothing else depends on — changeable in any release without invalidating anything already published. That is the point of naming the index as a drop-in escape hatch rather than building it.

## Machine Check

```bash
node -e "const{readdirSync,existsSync,readFileSync}=require('fs');const p=process.argv[1];let bad=[];for(const d of readdirSync(p,{withFileTypes:true}).filter(e=>e.isDirectory()&&!e.name.startsWith('.'))){const f=p+'/'+d.name+'/skill.json';if(!existsSync(f))continue;const j=JSON.parse(readFileSync(f,'utf8').replace(/^﻿/,''));if(Array.isArray(j.members)){if(typeof j.description!=='string'||!j.description.trim())bad.push(d.name+': group skill.json has no non-empty description');continue}if(j.description!==undefined)bad.push(d.name+': plain skill must not carry a description in skill.json');const s=p+'/'+d.name+'/SKILL.md';if(!existsSync(s)){bad.push(d.name+': plain skill has no SKILL.md');continue}const m=/^---\r?\n([\s\S]*?)\r?\n---/.exec(readFileSync(s,'utf8').replace(/^﻿/,''));const v=m&&/^description:[ \t]*(.*)$/m.exec(m[1]);if(!v||!v[1].replace(/^['\"]|['\"]$/g,'').trim())bad.push(d.name+': SKILL.md frontmatter has no non-empty description')}console.log(bad.length?bad.join('\n'):'OK');process.exit(bad.length?1:0)" ../hatch-skills
```

Expected result: `OK`, exit 0 — every top-level folder in the registry checkout sources its description from the right place: a group carries a non-empty string `description` on its own `skill.json`, and a plain skill carries one in its `SKILL.md` frontmatter and none in its `skill.json`. Any output names a folder that omits its description, leaves it empty, or authors it in the wrong file. This runs against a sibling `hatch-skills` checkout and fails until tasks 4.1 and 4.2 have landed there.

## Precedence

- Answers the open question [0027-testing-skill-convention](0027-testing-skill-convention.md) left for "a future registry discovery surface": testing content is omitted from an ordinary project's listing, exactly as it is unimportable there, and is shown as any other entry to a project recording `testProject: true`. That record stays accepted and unchanged; this one adds the listing rule it deferred.
- Builds on [0003-registry-github-tarball-fetch](0003-registry-github-tarball-fetch.md) — the same contents API, one more call shape, no second retrieval mechanism.
- Follows [0009-skill-versioning-semver-tags](0009-skill-versioning-semver-tags.md)'s and [0019-registry-removed-metadata-flag](0019-registry-removed-metadata-flag.md)'s precedent against index files, and [0016-group-member-manifest-format](0016-group-member-manifest-format.md)'s and [0019](0019-registry-removed-metadata-flag.md)'s precedent for additive optional fields on a folder's own `skill.json` rather than a separate file.
- Extends [0021-block-first-time-import-of-removed-target](0021-block-first-time-import-of-removed-target.md) onto a new surface: a removed entry a first-time import is refused is also a removed entry the listing does not advertise. That record's import behavior is unchanged.
- Accepts [0025-harness-shadowing-risk-accepted](0025-harness-shadowing-risk-accepted.md)'s ambiguity rather than resolving it — the fold-only-when-the-plain-folder-exists rule is that record's constraint applied to a listing, and a harness-exclusive family listing under its suffixed name is the cost it already accepted.
- Reads [0001-harness-suffix-convention](0001-harness-suffix-convention.md) for the reserved codes and for what `resolveSkillFolderName` actually resolves, which is what makes the fold rule truthful about what `hatch import` accepts.
- No known conflicting decision records.
